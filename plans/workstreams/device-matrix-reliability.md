# Workstream: device-matrix reliability — S3 pair, picos, drive-less CP transport

Status: **active.**  Opened 2026-07-05 (user call, same day as the 4-board bench expansion): "get both s3's working and the picos reliably, including the infra changes needed for circuitpython to work without a circuitpy drive."

## Goal

Every board on the bench deploys and sweeps green without hand-holding: the FeatherS3 pair (MP + CP), both picos, and a CircuitPython deploy path that does not require a mounted CIRCUITPY drive — which unblocks tinypico-cp (classic ESP32, no native USB, no drive possible) and removes the multi-volume UID-matching fragility on a bench that now mounts three CIRCUITPY drives at once.

## The load-bearing spike (2026-07-05, measured)

The user asked whether drive-less CP means a large new transport or whether the MP paths can be leveraged.  **Measured answer: the MP mechanics transfer.**  On the real tinypico-cp (CP 10.2.0 over a CP2104 serial bridge, no MSC anywhere), stock `mpremote exec` performed a file write, readback, and delete against `/`:

- CircuitPython implements the same raw REPL protocol the MP transport already speaks.
- On boards without native USB there is no USB host owning the filesystem, so the VM can write it freely — the exact property the MP transport's file-push depends on.

So phase 1 is a serial-mode CP transport that reuses the MP transport's raw-REPL file-write path, not a new subsystem.

## Phases

1. **Serial-mode CP transport (drive-less) — LANDED 2026-07-05.**  `CircuitpythonSerialTransport(CircuitpythonTransport)`: inherits every pyserial raw-REPL primitive, overrides only the six drive-touching methods; file writes stream as base64 chunks over the raw REPL; device-side scope/delete/clear scripts reused verbatim from `_device_scripts.py` (the genuinely shared, runtime-neutral layer).  All four bench-observed quirks handled (safe-mode probe fails loudly with the reason; OSC/CSI noise stripped in every read path; friendly-REPL ctrl-D so `code.py` actually runs; both autoreload spellings).  Selection: probe-driven auto (CP + zero CIRCUITPY volumes → serial) plus an explicit `deploy_transport:` devices.yml override; tinypico-cp un-parked with the explicit flag.  Hardware-proven on tinypico-cp: multi-file deploy incl. byte-exact binary round-trip, boot into code.py, console markers through the demo driver's MarkerQueue path.  40 unit tests, 98 % module coverage, preflight green.
   **New finding out of the hardware proof:** tinypico-cp exhibits *non-deterministic runtime corruption* under CP 10.2.0 regardless of transport — `'Runner' object has no attribute 'tick'`, `_adapter\x00` (NUL in an attribute name), a module imported as the wrong object; different each run, reproduces via plain `mpremote`, all deployed files byte-exact.  Smells like memory corruption in CP-on-classic-ESP32, not a deploy defect.  Discriminator experiment queued: swap the two TinyPICO units' runtimes — if corruption follows the runtime it's the CP classic-ESP32 port; if it follows the board it's this unit.
2. **feathers3-cp `WifiService` bring-up defect — SOFTWARE HALF FIXED 2026-07-05.**  Root cause: `CpWifiAdapter.connect()` re-issued `wifi.radio.connect()` without clearing the prior half-open station; on ESP-IDF (S3) a failed attempt poisons the next, so retries slow-fail in a cascade (2.4 s → 17 s → 19 s, intermittent `Unknown failure 205`) past the 45 s WIFI_OK budget.  Fix (wifi 0.7.1): `stop_station()` before each fresh attempt + already-linked short-circuit (mirrors the MP adapter's guard); 3 unit tests + an on-device repeated-failure test; WIFI_OK now 8/8 at ~4–5 s.  The `19a997dd` suspicion was a red herring (it only removed an unused surface).  **Hardware residual (user action):** this specific FeatherS3 unit measures 85–90 % packet loss to the gateway (control board: 0 %), reports MAC `00:00:00:00:80:AB` — a genuine RF/antenna defect in the unit; downstream socket-stage flakiness is the chip, not software.  Reseat/replace the board or add an external antenna.
3. **Pico reliability hardening.**  Both picos are green today; the fragility class to retire is drive *resolution* on a many-volume bench (UID mismatch errors when several CIRCUITPY drives mount, observed during the 2026-07-05 sweep).  Phase 1's serial mode is also the escape hatch here: native-USB boards keep the drive path as primary, but a serial fallback needs the boot.py `storage.remount()` / `storage.disable_usb_drive()` handshake — deliberately phase-3 (optional) because it touches what ships on every board.
4. **First-association grace.**  A freshly-erased ESP32 does RF calibration on its first wifi join and blows the demo driver's 45 s marker budget once, then passes warm (measured on both new boards).  Either warm the join during `add-device`, or give first-run sweeps a longer budget.
5. **UM P4-revision wifi instability (vendor-documented) + TX-power knob.**  Unexpected Maker documents wifi instability on pre-2024 P4/P7 ESP32-S3 board revisions — worst on channels < 6, at full TX power, with native USB enabled ([help.unexpectedmaker.com/docs/boards/wifi-stability-issues](https://help.unexpectedmaker.com/docs/boards/wifi-stability-issues/)).  The retired feathers3-cp is a P4 (user-confirmed) — its defect now has a vendor explanation.  Bench status: AP channel is 11 (safe); boards run full 20 dBm TX (the risky condition).  The replacement **tinys3-cp is also P4-family — ON WATCH**: swept green 2026-07-05 (demo PASS 42 s, first join 4.0 s, healthy MAC) but hears the AP at RSSI −82 (TinyPICO: −54), marginal headroom.  Queued mitigation: a `wifi.tx_power_dbm` config knob in WifiConfig/the adapters (CP `wifi.radio.tx_power`, MP `sta.config(txpower=)`) so P4 boards can run UM's recommended 75–90 % power via config.
