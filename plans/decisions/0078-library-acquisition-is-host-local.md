# Decision 0078: Library acquisition is host-local; the one deploy bundles it

Status: `accepted`
Date: `2026-05-18`
Summary: `chumicro-workspace library add` fetches full library trees from `ChuMicro-Libraries(-Experimental)` snapshot-tagged channels into committed `<workspace>/libraries/`; deploy bundles them.
Related: Decision [0077](0077-one-device-staging-path.md) (the one device-staging path — the deploy stage is the only board writer; this preserves it), Decision [0042](0042-library-dependency-policy.md) (a library's `pyproject.toml` `[project].dependencies` is the authoritative chumicro dependency graph), Decision [0018](0018-distribution-bundle-repo.md) (device-consumer bundle repos — this adds a sibling workspace-acquisition channel alongside them), Decision [0023](0023-standalone-promote-workflow.md) (the promote pipeline extended to publish the new channel), Decision [0074](0074-drift-mechanization-as-project-policy.md) (the drift lint that has no acquisition bypass to except), `plans/workstreams/deploy-path-unification.md`.

## Context

A regular-mode user starts from the workspace-template repo with no sibling chumicro checkout, and needs chumicro libraries to build against. Constructor injection plus Decision 0042 mean asking for one library implies its declared dependency closure (`mqtt` ⇒ `config`, `sockets`, `timing`, recursively). Users do not want these as opaque installed packages: they want to read the source, run the library's own tests and examples, and adapt a library to their needs inside their own project — keeping the test harness behind it — when the published version doesn't fit. Decision 0077 makes the deploy stage the only thing that writes a board, so acquisition must be a host-side operation that makes source resolvable, never a board write.

## Decision

**A chumicro library is acquired as a full, editable, committed source tree plus its declared dependency closure, pulled by a chumicro-owned downloader from a published channel. The deploy stage stays the only thing that writes a board, and user edits to an acquired tree survive everything but an explicit upgrade.**

- **Declarative, not discovered.** `chumicro-workspace library add <name>` (and `update`) is the acquisition act. The recursive `chumicro-*` closure comes from each library's `pyproject.toml` `[project].dependencies` — the same graph the bundle producer and dep-graph tooling already walk (Decision 0042) — not from any package-manager resolver.
- **One engine, two front-ends.** Acquisition has a single engine: resolve closure → download trees → record in the `libraries:` table. A TTY-only interactive browser (multi-select a set, toggle stable/experimental, read each library's description, drill into its README or an example and return to the list) is a front-end that ends by calling that engine; `library add <name>… [--channel] [--pin]` is the non-interactive front-end over the same engine — TTY auto-detected, the scriptable path never prompts, distinct exit codes per failure. Two front-ends, never two acquisition paths. Browsing and drill-in read a lightweight catalog the channel publishes (per-library name, version, description, README) and never clone trees; the full closure downloads only on confirm.
- **Full tree, into committed source.** Each acquired library lands at `<workspace>/libraries/<name>/` carrying `src/`, `tests/`, `examples/`, `docs/`, `functional_tests/`, `pyproject.toml`, `README.md`, `VERSION` — identical to its shape in the chumicro source tree — and is recorded in `workspace.yml`'s `libraries:` table (channel, pinned/floating, resolved version). The tree is the user's source to read, run, and edit in place; it is committed, so a fresh clone reproduces a deploy with no refetch.
- **Dedicated published channel, snapshot-tagged.** Full-tree repos — `ChuMicro/ChuMicro-Libraries` (stable) and `ChuMicro/ChuMicro-Libraries-Experimental` (pre-release) — published by the same promote pipeline that builds the device bundles (Decision 0018 / 0023), and tagged with the same whole-repo snapshot model: a tag is every library's full source tree as of that release, carrying a per-snapshot manifest (library → version). The device bundles stay deploy-flattened `.py`+`.mpy`+`package.json` for circup/mip consumers; this channel carries the source tree for host-side workspace acquisition. This is deliberately the circup/mip mental model — channel = repo, latest tag is the default, channel switch = repo switch, no version solver.
- **Closure from one snapshot.** A library's `pyproject.toml` declares bare dep names, no version constraints (Decision 0042), so the correct dependency set is definitionally the one built together in a single snapshot. `add` resolves the closure and fetches every member from one tag (default: latest). Pinning is to a *snapshot* — the internally-consistent set as of tag T — not per-library: holding one library at an old version while others advance assembles an untested mixed-snapshot closure the no-version-constraint pyprojects cannot make sound. Per-library version pinning is out of scope here and tracked as an open question (it is a pyproject-versioning-metadata decision, not a transport one).
- **Chumicro-owned downloader.** The tagged snapshot is fetched as a single tarball over HTTPS by a downloader this project owns — no `pip`, `circup`, or `mip` on the acquisition path — and only the manifest-listed closure subtrees are extracted into `libraries/`; the rest is discarded. The manifest is fetched alone when only resolution (not download) is needed.
- **Edit-preserving upgrade.** An acquired tree is never overwritten implicitly; `add` of an already-present library is a no-op on its tree. `update`/upgrade is explicit and edit-safe: the current tree is copied to an untracked, gitignored `<workspace>/_library-backups/<name>/<old-version>-<timestamp>/` before replacement, so a user who adapted the library can lift their changes back. Pinned entries skip; floating entries upgrade.
- **Host-local invariant (Decision 0077).** Nothing here writes a board. The import-graph deploy roots on the committed `libraries/<name>/src/` exactly as it roots on a dev-mode sibling checkout — a fetched library and a hand-cloned one are indistinguishable to the deploy. Dev mode's `library_sources:` (a local sibling checkout, not a fetched artifact) is unchanged.

## Rejected

- **`pip` / `circup` / `mip` as the acquisition backend.** Each runs its own dependency resolver — fighting the authoritative pyproject graph — and emits a flattened importable package plus `.dist-info`/`bin/`, with no `tests/` or `examples/` to run or read. The device bundle repos are package-only by the same design (circup/mip consume flattened `.py`+`.mpy`) and cannot carry the tree workspace acquisition needs.
- **Discover what to fetch by AST-walking the project's imports.** A fresh project imports nothing yet, and a library can't be imported until it's acquired — discovery is empty exactly when acquisition is needed. Acquisition is declarative; an import walk's only honest role is a non-fetching coverage check ("you import `chumicro_foo` but haven't added it").
- **A gitignored, tool-managed cache tree.** The user can't see, run, edit, or commit it, and a fresh clone can't reproduce a deploy. Vendoring into the committed `libraries/` tree is the feature, not a cost.
- **Auto-fetch inside `deploy` on an import-graph miss.** Couples a network fetch into the staging path and re-tangles "acquire" with "stage"; weakens the offline story. Acquisition and the one deploy stay separate.
- **Clobber on update.** Destroys user adaptations silently. Upgrade backs up first.

## Consequences

- One acquisition path, one manifest (the `libraries:` table), one `update`/pin story. The regular-mode/dev-mode split shrinks to *where the tree came from* (published channel vs local sibling checkout); both resolve through the committed `libraries/<name>/` the deploy walker already roots on.
- A user can read any acquired library, run its tests and examples, and adapt it — all inside their own repo, never visiting chumicro. Adaptations survive everything except an explicit upgrade, which preserves the prior tree in an untracked backup.
- Two new release-channel repos; the promote pipeline (Decision 0018 / 0023) is extended to publish full library trees alongside the device bundles, plus a per-channel catalog index (name, version, description, README) the pipeline already has the aggregation for. Cross-repo isolation holds — the workspace pulls from a published channel, not the mono-repo.
- The interactive browser and the non-interactive `library add` share one engine, so the one-acquisition-path invariant holds across both; agents and CI use the non-interactive front-end (no TTY, scriptable, exit-code-classified) with no second code path to drift.
- The versioning/closure/channel behavior matches circup/mip by design, so no third paradigm to reason about; what this adds over them is committed-source, edit-preservation, and the browser, not a different version model. Sound per-library version pinning would require version constraints in library `pyproject.toml`s — tracked in [`plans/open-questions.md`](../open-questions.md), out of scope for this ADR.
- Decision 0077's "only the deploy stage writes a board" holds with no CLI bypass; Phase 5's drift lint (Decision 0074) has no acquisition channel to except.
- The workspace-template `.gitignore` ignores `_library-backups/`; the regular-mode README documents `library add` / `update` as the acquisition recipe.
