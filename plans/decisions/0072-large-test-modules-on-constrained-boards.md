# Decision 0072: Chunked test-module exec + opt-in per-file reset for the on-device sweep

Status: `accepted`
Date: `2026-05-17`
Related: [Decision 0071](0071-per-library-soft-reset-flash-sweep.md) (per-library reset — this extends it to opt-in per-file granularity; its "Not closed" per-file thread resolves here), [Decision 0068](0068-unified-deploy-mode-resolution.md) (the on-device unit sweep), [Decision 0027](0027-device-testing-infrastructure.md) (persistent raw-REPL execution model), [Decision 0028](0028-deploy-modes.md) (transport `soft_reset()`), [Decision 0016](0016-cross-runtime-unit-tests.md) (cross-runtime discovery — the forcing function), [Decision 0015](0015-board-architecture-support.md) (256 KB minimum board).

## Context

Cross-runtime class discovery now runs large class-organized test modules on-device that previously ran CPython-only. On a 256 KB board (Pi Pico W CP/MP) in flash device-unit this exposed **two distinct memory walls**; PSRAM boards (Lolin S2) hit neither (websockets 288/0/0 on CP+MP). Decision 0071 closed cross-library `sys.modules` accumulation but explicitly left per-file reset open and tracked it to `plans/open-questions.md`. This decision resolves both walls.

## Decision

### 1. Chunked module exec (wall 1 — compile transient) — implemented

MicroPython / CircuitPython compile a whole `exec()` argument at once; a ~1200-LOC class module's compile peak alone exceeds 256 KB. The host (CPython, has `ast`) computes decorator-aware top-level statement start lines (`_test_runner.chunk_boundaries_for`); the device execs the file in per-statement chunks into one shared namespace (`discovery._exec_chunked`), bounding the compile peak to the largest single statement. This is semantically identical to one `exec` (shared globals, source order). Chunks are newline-left-padded so tracebacks keep real source line numbers. `chunk_boundaries=None` keeps the single whole-file exec (CPython / unix-port unchanged); a `from __future__` import or fewer than two top-level statements disables chunking (each chunk compiles independently). Implemented with plain list ops — no PEP 448 set unpacking; this module runs on-device.

### 2. Opt-in `--per-file` — implemented

Wall 2 has **two** sub-problems on a Pi Pico W, both addressed by `--per-file`. The first was found on the bench 2026-05-17 and corrects the original "wall 2 is purely a RAM resident ceiling" framing:

- **Flash drive capacity (the binding wall a *heavy* library hits first).** The default sweep bulk-stages a library's *entire* test suite + its src + the harness in one rsync. A heavy library's full suite + src + harness exceeds the **~491 KB Pi Pico W CIRCUITPY drive**, so rsync fails `No space left on device` (on a library src file) *before any test executes* — not a RAM event, not recoverable by `reset-board`, and identical to a RAM failure in the bare `F` pattern until you read the rsync error. `--per-file` stages **exactly one test file at a time** (that file + src + harness), and rsync `--delete` drops the prior file — and the prior library — so the drive stays bounded well under 491 KB.
- **RAM resident ceiling.** Even once staged, one very large module's resident defs + the library + the harness can exceed 256 KB on a fresh interpreter running that file alone — distinct from Decision 0071's cumulative `sys.modules` (a single file on a fresh board still OOMs; verified on hardware). `--per-file` soft-resets the VM before each file (Decision 0071's per-library reset extended to per-file granularity), giving each file `library + one file + harness` with no accumulation; a single file still over the RAM ceiling is resolved by the §3 split policy.

The deliberate cost: `--per-file` re-rsyncs src + harness per file (the default bulk path rsyncs them once per library). `--per-file` exists for the constrained board, where *fitting the 491 KB drive at all* matters more than rsync count. The default stays the fast per-library bulk-stage path — PSRAM boards and ample-flash targets do not need per-file granularity. Implemented in `chumicro_pytest_device.plugin` (the `is_filesystem_mode and _session_per_file` branch in `DeviceRuntimeBackend.prepare`); the earlier implementation bulk-staged the whole suite even under `--per-file`, which is exactly what overflowed the drive — fixed 2026-05-17.

### 3. Every test file must run green on a freshly-reset Pi Pico W (CP + MP) — required

`--per-file` is the *mechanism*; this is the *policy* it serves. Every cross-runtime test file must run green on a freshly-reset Pi Pico W under **both** CircuitPython **and** MicroPython. A file whose resident defs + library + harness exceed the board's budget — so it OOMs even alone on a fresh interpreter with `--per-file` — **must be split** until each resulting sub-file fits. Splitting mirrors source modules where one exists; past that it is mechanical and lossless (test bodies preserved byte-identical, as the `requests` cohesion split demonstrated). A file that OOMs on the 256 KB board is a tracked defect to resolve by splitting, not an accepted end-state.

There is still **no rigid universal tests-per-file cap and no CHU lint** — the resident ceiling is library-weight-dependent (a heavy `_wire`-backed library hits it far sooner than a light one; coarse Pi Pico W CP data: ≈32 tests/file passes, ≈61 OOMs — and the CP and MP ceilings differ). A fixed number would misfit most files. The criterion is empirical and bench-determined **per library**: split until a freshly-reset Pi Pico W runs every one of that library's files green on CP and on MP. This ADR owns the policy and its doc home (`docs/contributing/device-testing.md` + the `/audit-library` + `/audit-embedded` pointers), now framed as a requirement, not a caution.

**Why this is required, not optional.** The Pi Pico W (264 KB, CP and MP) is a *distinct memory HAL* from the PSRAM Lolin S2 (2 MB). A test passing on PSRAM does not validate the constrained-memory path — which, for libraries whose entire reason to exist is the 256 KB tier ([Decision 0015](0015-board-architecture-support.md)), is the path that matters most. Leaving large files un-run on the Pico W silently drops HAL coverage on exactly the boards the libraries target, on both runtimes. The split work is lossless and the only cost is file count and bench iteration; that cost buys real two-HAL validation and is worth paying.

### Alternatives considered

- **Sub-batch within a file (reset between batches, re-import the library per batch).** More code, slower (re-import per batch), and a file too big to compile-or-hold needs chunked exec anyway. Per-file reset is the simpler grain and the standard embedded-test-harness shape (MicroPython's own runner runs files independently for memory isolation).
- **Rigid tests-per-file cap + CHU lint.** The ceiling is library-weight-dependent, not universal (and differs CP vs MP); a fixed cap is wrong for most files and over-restrictive everywhere. The empirical per-library "split until the freshly-reset Pico W runs it green on both runtimes" criterion is what closes the requirement without a misfitting universal number.
- **Document a per-board ceiling only, no mechanism.** Distinct from Decision 0071's rejected "document a library ceiling": 0071 refused to punt a *reducible* cross-library accumulation; here `--per-file` (one-file staging + fresh-VM reset) *is* the mechanism, and the split requirement covers only the *irreducible* residual (one file too large to be resident even alone — physics, not accumulation). Not a contradiction of 0071.
- **Reactive split only — split a file *after* it is observed to block a sweep, treat the OOM as acceptable sweep output until then.** Rejected: this leaves the 256 KB tier under-validated on exactly the libraries that target it, indefinitely, and only on the boards where coverage matters most. The `requests` test-quality audit confirming the suite is not over-tested means splitting is not test-reduction — it is a lossless reorganization in service of two-HAL coverage. Splitting is required for every over-ceiling file, not deferred until a sweep happens to trip on it. (Source-cohesion splits like requests `_wire`-vs-`client` still proceed on readability grounds independently; they are not a substitute for splitting *small enough* to fit — requests' own 89/83-test halves are still over the Pico W ceiling and need further splitting.)
- **Accept the ceiling, no per-file mode, run large suites on PSRAM only.** Rejected: leaves the cheapest supported board class — the one the libraries exist for — unable to run the on-device sweep it exists for, while PSRAM boards mask the gap. Abandons two-HAL validation of the 256 KB tier for large suites.

## Consequences

- Wall 1 is closed (chunked exec landed). Any module that is compile-heavy but resident-OK now runs on a 256 KB board where it previously OOM'd at compile.
- Decision 0071's "Not closed by this decision" per-file-reset thread is resolved here (0071 edited in place to point here); `plans/open-questions.md` thread 1 closes on `--per-file` landing.
- Default sweep behavior is unchanged (per-library reset). `--per-file` is opt-in, materially slower, and is the path used to validate the Pico W per-file requirement.
- `device-testing.md` and the `/audit-library` + `/audit-embedded` pointers state the Pico W per-file coverage **requirement** (not a caution); `--per-file` is implemented so the mechanism is real.
- The over-ceiling files are a **required, scheduled, bench-iterated split backlog**, not an optional reactive set: `websockets/test_websockets.py` (136), `websockets/test_client.py` (77), `websockets/test_server.py` (61), `http_server/test_http_server.py` (123), `mqtt/test_client.py` (80), and `requests/test_wire.py` (89) + `requests/test_client.py` (83) — the last two are above the coarse Pico W OOM datapoint *despite* the source-cohesion split, so `requests` needs further splitting. Exact targets are bench-determined per library on CP and MP.
- Reconciles with the on-device sweep contract (`device-testing.md`; deploy-mode-unification 4d): the sweep still does not hard-fail `preflight` on a per-library on-silicon OOM, so a run completes and reports. But a Pico W per-file OOM on CP or MP is now a **tracked defect to fix by splitting**, not an accepted terminal output — "output, not a gate" governs how the sweep *runs*, not whether the gap is acceptable. The end-state is zero per-file OOM on a freshly-reset Pico W once the split backlog clears.
- The flash-mode per-file-reset gap is a recorded, resolved design property, with a standing requirement that keeps it from silently reopening as suites grow.
