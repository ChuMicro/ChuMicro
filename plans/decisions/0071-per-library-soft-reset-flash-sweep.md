# Decision 0071: Per-library soft-reset in the flash/copy device sweep

Status: `accepted`
Date: `2026-05-16`
Summary: pytest-device issues `transport.soft_reset()` before staging each library in flash mode; new `clear_entrypoints()` clears `code.py`/`main.py` once per session; MP copy mode deletes per-library.
Related: [Decision 0068](0068-unified-deploy-mode-resolution.md) (the on-device unit sweep — this resolves its Phase 4b.2 issue (ii)), [Decision 0028](0028-deploy-modes.md) (RAM/flash transport semantics — `soft_reset()` already exists on both transports), [Decision 0070](0070-host-only-test-marker.md) (issue (i), the *other* half of the 4b.2 split — disentangled from this by experiment), [Decision 0044](0044-deploy-time-runtime-filtering.md).

## Context

Decision 0068's on-device unit sweep runs ~15 libraries in **one** pytest session over **one** persistent device raw-REPL session. The pytest-device plugin issues `transport.soft_reset()` between staging steps **only** in the RAM/mount branch (`transport.mode in ("ram", "mount")` → `_should_soft_reset_before_stage`). The `is_filesystem_mode` (CP-flash, MP-copy) branch re-stages per library via rsync `--delete` but **never soft-resets** — the interpreter persists, so `sys.modules` from every library accumulates and is never evicted.

On a 264 KB-RAM Pi Pico W this exhausts the heap. Instrumenting `gc.mem_free()` at each library switch showed free memory declining to a stable ~70 KB plateau (stable because it is all *live* imported modules — `gc.collect()` reclaims nothing; it is not a leak). The device then fails to `exec()` the larger test modules: `runner/test_core` (60 tests), `wifi/test_wifi` (41), `msgpack/test_msgpack` fail wholesale with `MemoryError: memory allocation failed` in `chumicro_test_harness.discovery._exec_as_namespace`, while the same files pass standalone on a fresh interpreter. A controlled experiment (Decision 0070's host-only fix excludes ~70 unrelated issue-(i) failures) confirmed these failures are independent of issue (i) and reproduce identically with memory stable and the transport alive — disproving the earlier "transport dies at scale" and "leak" hypotheses.

The same latent gap exists for CP functional flash tests (they share `_stage_to_flash`, which deliberately does not soft-reboot to keep the harness raw-REPL session alive), but is masked because a functional run is almost always scoped to one library. `deploy_files` (the production app-deploy path, not the test harness) already Ctrl-D-reboots after rsync. MicroPython's normal sweep mode is `mount`, which routes through the RAM/mount branch and already resets — so the cumulative-`sys.modules` symptom is CP-flash-specific in practice only because CP RAM-mode hard-crashes `wifi` (the separate 4c item), leaving flash as CP's only viable sweep path.

MicroPython **copy** mode (`--deploy-mode flash` on MP) has a *second, independent* defect this decision's per-library reset turned from a single-library failure into a sweep-wide cascade. CP flash staging is rsync with `--delete`, so each library switch cleans the prior tree off the drive; the MP copy transport stages with `mpremote fs cp -r`, which only adds/overwrites and has **no `--delete` analog**. A multi-library sweep therefore piles every library's package tree onto the device LittleFS until it fills — verified on a Pi Pico W: nine libraries staged cleanly, then `requests` hit `mpremote: cp ... No space left on device`. The `ENOSPC` wedges the board's USB-CDC (`OSError [Errno 6] Device not configured`); the per-library `soft_reset()` introduced here then runs `mpremote connect <port> reset` against a re-enumerating port (`it may be in use by another program`), fails, and — because nothing rode out the re-enumeration window — every subsequent per-library reset failed too (139 failed / 275 passed; `runner`/`wifi`/`timing` were cascade victims, not real failures).

## Decision

The pytest-device plugin issues `transport.soft_reset()` in the `is_filesystem_mode` branch **before staging each library** (including the first — the run never inherits whatever VM state the board happened to boot with). The reset is *before* the rsync, not after, giving a fresh interpreter (cleared `sys.modules`, full heap) *without* surrendering execution control to a natural `code.py` boot (which the harness needs for structured raw-REPL output, the Decision 0027 model). `_push_staging_to_drive` then disables autoreload, rsyncs, and the harness runs the tests over the live raw-REPL session. Each library's tests then `exec()` exactly as they do standalone and as mount/RAM mode already gets per-file. `soft_reset()` already exists on both the CircuitPython and MicroPython transports; the same `pytest.fail`-on-error handling as the RAM/mount branch applies.

`soft_reset()` (Ctrl-D reboot → Ctrl-C ×2 → Ctrl-A → verify raw-REPL prompt) is racey *in isolation*: a stale app `code.py` left on the drive by a prior `deploy-example`/project deploy would start running on the reboot before the Ctrl-C lands, and an adversarial one (hard-fault / `microcontroller.reset()` / uninterruptible) could make the sweep flaky (loud-fail, never silent — `_enter_raw_repl` raises if the prompt is absent). The sweep's rsync excludes `code.py`/`boot.py`, so it neither writes nor removes such a file. To remove the race rather than rely on "in practice the board lands cleanly," the plugin calls a new `transport.clear_entrypoints()` **once per device, before the first `soft_reset()`**: it deletes `code.py`/`main.py` and verifies they are gone — CircuitPython unlinks host-side then `flush_volume`s so the deletion is on the physical FAT before the reboot re-reads it and polls the drive to confirm (raising loudly if an entrypoint survives the budget); MicroPython runs `os.remove` + re-`stat` *on the device* (authoritative immediately, no host-FAT lag). A single clear holds for the whole session because the sweep never writes an entrypoint. With no `code.py`/`main.py` present, every subsequent reboot drops straight to a clean REPL — the timing assumption is eliminated, not merely unlikely to bite. RAM/mount transports never persist an entrypoint, so `clear_entrypoints()` is a no-op there.

### Alternatives considered

- **Chunk the sweep into sub-sessions (fresh transport per N libraries).** Heavier — full reconnect + transport teardown cost, more board churn — to achieve what one `soft_reset()` (Ctrl-D + re-enter raw REPL, already paid per-file in mount mode) achieves. The board and transport are healthy; only the VM's module table is the problem.
- **Document a per-board library ceiling.** Punts the defect onto every caller, is fragile (ceiling shifts with library size), and defeats the sweep's purpose (validate the whole library set on silicon).
- **Full transport reconnect between libraries.** Strictly more expensive than `soft_reset()` and unnecessary — the serial transport and FAT volume are fine across the session (the probe stayed responsive throughout); the cumulative state is purely interpreter-side.
- **RAM mode only (no flash sweep on CP).** Not available — CP RAM-mode hard-crashes `wifi` (the 4c item), so flash is CP's only viable sweep path.

## Consequences

- Decision 0068 Phase 4b.2 issue (ii) is resolved; the `plans/open-questions.md` "How does the on-device sweep survive a full-scale run…" entry is closed on the confirming re-run.
- The flash/copy sweep gains a per-library fresh interpreter, matching mount/RAM. Per-switch cost is one Ctrl-D + raw-REPL re-entry — the same operation mount mode already pays per file, amortized across a whole library's batch.
- CP functional flash tests were **also latently affected and are also fixed by this change**: `scripts/run.py test-libraries-functional` (and `preflight --with-functional`) with no `--library` runs *every* library's `functional_tests/` in one pytest invocation over one persistent flash session, so `sys.modules` accumulated across libraries there too — it just had not been run at a scale that exhausted the heap before the unit sweep exposed it. The fix is in the shared `prepare()` `is_filesystem_mode` library-switch branch, so it covers unit and functional multi-library flash runs identically. The deliberate "no soft-reboot in `_stage_to_flash`" property (keeps the harness raw-REPL session alive mid-file) is unchanged — the reset happens between libraries at the plugin layer, not inside the transport's stage.
- The `soft_reset()` stale-`code.py` race is **closed** for the sweep by `clear_entrypoints()` (a new `TransportProtocol` method, no-op on RAM/mount): the timing assumption is removed because no entrypoint is present to race. A bounded host-side poll after `flush_volume` makes a non-committed FAT delete a loud failure, never a silent one.
- **MP copy-mode `--delete` analog + reset hardening (the second defect above):** the MicroPython copy transport now deletes the previously-staged top-level tree from the device before each `fs cp` (a device-side recursive remove of exactly the roots the last `stage()` wrote — the copy-mode equivalent of the CP flash rsync `--delete`), so the LittleFS no longer fills across a multi-library sweep. Independently, the subprocess reset path (`recover()` and `soft_reset()`'s no-serial fallback) now rides out a USB-CDC re-enumeration with a bounded settle-and-retry and settles once after a successful reset, so a single hard failure (the `ENOSPC` above, or any wedged board) can no longer cascade through every subsequent per-library reset — it raises a loud error or recovers, never silently fails the whole sweep. Largest single staged set is ~330 KB (websockets) against the Pi Pico W's ~848 KB, so per-library cleanup leaves wide headroom.
- **Not closed by this decision:** within a single library, multiple test *files* in flash mode still run on one session with no per-file reset (RAM mode resets per file via `_should_soft_reset_before_stage`; flash mode does not) — addressed by [Decision 0072](0072-large-test-modules-on-constrained-boards.md), which adds an opt-in `--per-file` reset for large class-organized modules whose resident cost (not cumulative `sys.modules`) exceeds a 256 KB board. The harness still runs test bodies via persistent raw-REPL `execute()` rather than a natural `code.py` boot (a deliberate Decision 0027 tradeoff for speed + structured output); that natural-boot question remains tracked in `plans/open-questions.md`. This decision closes the cross-library cumulative-`sys.modules` exhaustion and the reset race.
- The flash/mount asymmetry is now an explicit, recorded design property rather than an implicit gap that surprised a reader who knew the codebase. Decision 0068's workstream Status (4b.2) is edited in place to point here.
