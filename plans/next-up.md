- [ ] **`chumicro_mqtt._attempt_self_heal` runs inside `handle()` and stalls the runner** — `socket_factory()` synchronously does DNS + TCP + TLS handshake (seconds on a slow link), blocking every other registered service for the duration.  The reference impl's pattern is reconnect-in-user-space: `loop()` raises on a dead connection and the application reconnects from `main` outside the loop, so the loop itself never blocks.  Two options: (a) match the reference and remove self-heal entirely (caller handles reconnect), or (b) keep self-heal but break it across ticks via a state machine (CLOSING → AWAITING_FACTORY → CONNECTING → AWAITING_CONNACK).  Initial `connect()` blocking is NOT a contract violation — by convention it runs before the runner loop starts.  Needs an ADR to pick (a) or (b).  Deferred from convergence step 6 polish.
- [ ] **`chumicro_runner.add_periodic` phase slip on a 1 Hz schedule** — observed ~1.08 s per publish on Pi Pico W CP custom firmware (2026-05-23, post-step-1+2 bake), ~8% slow, compounds across long runs.  `Runner.tick` at `libraries/runner/src/chumicro_runner/core.py:318` reschedules a fired periodic as `entry.next_due_ms = ticks_add(now_ms, entry.period_ms)` — re-anchoring from *now* instead of from the previous deadline.  When the handler takes 50 ms (publish + send + ack-wait), the next fire shifts ~50 ms later every period; metering / sampling tasks would lose phase.  The drift-resistant alternative is `ticks_add(entry.next_due_ms, entry.period_ms)`.  Tradeoff: phase-preserving rescheduling causes catch-up bursts after a long stall (5 fires in 10 ms if the board was busy 5 s), which is wrong for LED / UI tasks.  Cleanest fix is probably a per-registration knob (`catch_up=False` default for current behaviour, opt-in phase preservation for sensing) — needs an ADR.
